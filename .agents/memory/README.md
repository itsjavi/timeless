# Agent Memory Guide

`.agents/memory/` stores agent-facing context and planning artifacts for Timeless UI work.

## Structure

```text
.agents/
  memory/
    README.md
    DESIGN.md
    milestones/
      001-example-slug/
        PLAN.md
        TASKS.md
        RESULTS.md
```

## Design Guide

Use `.agents/memory/DESIGN.md` as the design source of truth for UI work in `apps/stories`,
`packages/components`, and `packages/core`. Read it before creating or changing component styles,
StoryLite stories, visual states, overlays, form controls, or core behavior that affects UI
authoring.

## Milestones

Use `.agents/memory/milestones/` for big changes, including cross-cutting component work, new public
APIs, architecture changes, package/app additions, or work that needs multiple implementation steps.

Milestone folders must be numbered and named in this format:

```text
XXX-short-slug
```

Examples:

```text
001-initial-master-plan
002-dialog-focus-management
```

Choose the next number by inspecting the existing milestone folders. Keep slugs short and lowercase,
using hyphens between words.

## Milestone Status

`PLAN.md` starts with YAML frontmatter declaring the milestone's status:

```markdown
---
status: Accepted
---

# Milestone 021 Plan: ...
```

`status` is exactly one of:

- `Proposed`: drafted, not yet agreed to run.
- `Accepted`: agreed and scheduled, implementation not finished.
- `Implemented`: the work landed and `RESULTS.md` records it.
- `Rejected`: will not be implemented. The folder stays to keep milestone numbering sequential.

The status lives only on `PLAN.md`, and it is the one part of that file that is expected to change
after creation. Everything else in `PLAN.md` stays as written; the divergence between plan and
outcome belongs in `RESULTS.md`.

## Milestone Files

Each milestone must contain these files:

- `PLAN.md`: the static implementation plan. Write the intended approach, scope, sequencing,
  constraints, and acceptance criteria before implementation. Once work starts, avoid rewriting this
  file to match what happened later.
- `TASKS.md`: the live todo list for the agent. Use Markdown checkboxes and update them as work
  progresses. Mark a task done only when it is complete. It is okay to add, split, mark, or unmark
  tasks as the implementation changes.
- `RESULTS.md`: the concise implementation record. Capture constraints found during the work,
  trade-offs, important implementation decisions, and a summary of the changes made. Do not repeat
  the full plan or task list.

Small, localized changes do not need a milestone unless the user asks for one.

## Model Attribution

Every milestone file ends with a horizontal rule followed by an attribution line naming the agent
and model that actually generated the document, including the reasoning effort when the agent
exposes one:

```text
---

Generated by Claude Opus 5 - Max reasoning
```

Name whatever produced the file, for example `Generated by Codex GPT-5.6 Sol`. Apply it per file:

- `PLAN.md` and `TASKS.md`: add the `Generated by` footer when the file is created.
- `RESULTS.md`: add the same `Generated by` footer, plus an `Implemented by` line naming the model
  that implemented the milestone. Never fill `Implemented by` when the milestone docs are created;
  add it only after the implementation work happens, and keep it accurate if a different model
  finishes the work.

This convention applies to new milestone files. Existing milestones without footers stay as they
are.
