# AGENTS.md

Guide for AI coding agents working in this monorepo.

## What this repo is

This repository is a multi-app multi-package monorepo hosting everything about "Timeless UI",
Timeless for short.

Timeless is a framework-agnostic UI library based on modern web standards. Read more about it in the
@README.md file.

## Agent memory planning workflow

Use `.agents/memory/` for agent-facing project context and implementation planning.

- Read `.agents/memory/README.md` before creating or updating planning artifacts.
- For big changes, create or use a milestone under `.agents/memory/milestones/` named `XXX-slug`.
- Each milestone must contain `PLAN.md`, `TASKS.md`, and `RESULTS.md`.
- `PLAN.md` carries a `status:` frontmatter field. `.agents/memory/README.md` defines the permitted
  values and when each applies.
- End every milestone file with the model attribution footer defined in `.agents/memory/README.md`:
  `PLAN.md` and `TASKS.md` get a `Generated by` line, and `RESULTS.md` additionally gets an
  `Implemented by` line once implementation happens.
- Treat `PLAN.md` as the static implementation plan. Do not rewrite it to match work already done.
- Use `TASKS.md` as the live todo list. Mark tasks done only after they are complete.
- Use `RESULTS.md` to capture constraints, trade-offs, implementation decisions, and a concise
  summary of what changed.

## Rules for authoring components

- Prioritize CSS-only components that don't require JS, unless we need to support A11Y features
- Prefer anchor-positioning, native popover and dialogs, over fake ones or JS-based positioning
  (unless there is no other choice)
- Follow WCAG and the WAI-ARIA Authoring Practices Guide patterns for every component with semantics
  or interaction: https://www.w3.org/WAI/ARIA/apg/patterns/
- Prefer native HTML semantics before ARIA. Add ARIA only when it completes a native contract, and
  never use ARIA to replace missing DOM behavior.
- Interactive components must implement the keyboard behavior, focus handling, accessible names,
  descriptions, roles, states, and relationships expected by the relevant APG pattern.
- Decorative anatomy and generated behavior hooks must be hidden from assistive technology when
  appropriate, and stories must show copyable markup with proper labels and relationships.
- When CSS is not enough, prefer Light DOM over Shadow DOM.
- Components must remain usable without the Atmosphere theme. `tokens.css` and `core.css` are
  required — core is behavior, not appearance — but a consumer must be able to drop the theme and
  style the public anatomy with their own CSS or utility classes.
- Keep all consumer-facing and customizable styling in CSS files. Component JS must not write visual
  declarations such as colors, spacing, borders, shadows, layout, position, inset, transforms, or
  animation styles directly.
- JS may set behavior attributes, ARIA and platform state, private `data-ui-internal-*` runtime
  hooks, or CSS custom properties for measured values. TS may use CSS tokens or custom properties in
  inline styles only when there is no reasonable CSS-only alternative, and must keep that usage
  minimal. CSS files should still own how runtime hooks render visually.
- Prefer author-owned Light DOM for style-relevant anatomy. Core JS should enhance existing markup
  instead of creating visual elements.
- Core JS may generate behavior-support elements only when the generated element is optional,
  documented, and stylable through a stable public API before it is shown.
- Do not create visual class names in component JS. JS may set behavior attributes and properties
  such as `id`, `hidden`, `popover`, `aria-*`, and `tabindex`, but visual styling must remain in
  CSS.

## Rules for authoring attributes

- Native CSS components use a `.ui-*` root class. Contract-declared visual configuration uses
  `data-ui-*`, for example `<button class="ui-button" data-ui-variant="primary">`.
- Every `ui-*` tag must be a registered behavioral custom element. Public host configuration uses
  plain attributes, for example `<ui-tabs orientation="vertical" activation="manual">`.
- Boolean custom-element attributes should use presence/absence, e.g. `invalid`, `wrap`, and
  `attached`, not string values like `data-ui-invalid="true"` or `data-ui-wrap="false"`.
- Do not use `data-ui-*` as configuration on `ui-*` custom-element hosts. CSS and JS for public host
  state should target the plain attributes, e.g. `ui-menu[orientation='horizontal']`.
- Authored Light DOM anatomy uses a whitespace-separated `data-ui-part` token list. Select tokens
  with `[data-ui-part~='name']` and keep each part owned by its nearest component root.
- Native attributes, ARIA, and platform pseudo-classes are authoritative for public state.
- Custom-element host state with no public attribute equivalent uses `ElementInternals.states` and
  `:state()`. Unavoidable child runtime hooks use private `data-ui-internal-*` attributes.
- Do not expose diagnostics or runtime state through public `data-ui-*` attributes.
- Story anatomy factories must emit the same public API expected from consumers: plain attributes on
  `ui-*` custom elements, contract-declared configuration on native roots, and `data-ui-part` for
  authored anatomy. Copied source must never contain `data-ui-internal-*`.

## Rules for declaring permitted values

- Permitted attribute values are declared once, in `valueSets` in
  `packages/components/scripts/component-registry.mjs`. An attribute references a set by name
  through `set:` and never inlines a value list.
- `pnpm generate` projects those sets into `src/values/<module>.ts`, `src/contracts.ts`,
  `src/attributes.ts`, `custom-elements.json`, the framework typings, and the editor data. Never
  hand-edit a generated file; change the registry and regenerate. The full list of generated files
  is in `.agents/reference/generated-files.md`.
- Modules that already export a value array re-export it from their `src/values/<module>.ts` and
  keep their own type guards. A public export must never change name or module.
- Sets with identical values keep separate names when they are separate public exports.
  `buttonSizes`, `primitiveSizes`, and `formControlSizes` are all `sm | md | lg`.
- `pnpm -F @timelessui/components run contracts:validate` proves every set against the stylesheets
  in both directions. A value the CSS selects must be declared, and a declared value must be
  selected or be the attribute default.
- Declare each element's events with the detail type that element actually dispatches, not the
  shared `UITransitionDetail`. `pnpm -F @timelessui/components run manifest:validate` fails when the
  named type is not exported.
- Never hand-copy a value list into `argTypes.options`, an example factory, or a test. Import the
  exported array.

## Rules for writing `.stories.ts` files

- Prefer one component per story file. Title it `Library/<Group>/<Component>`, where `<Group>` is
  the catalog group — e.g. `Library/Actions/Button`, `Library/Feedback/Badge`,
  `Library/Content/Card`. `write-route-catalog.mjs` fails the build on implementation-oriented
  prefixes such as `CSS Primitives/`, and the route id itself comes from the story filename through
  the `storyDomains` table in `apps/stories/.storylite/config.ts`, not from the title.
- Every component story file must export a `Default` story. Use `Default` for the default view with
  useful args and controls.
- Additional story exports should show meaningful demos that are different from the default view and
  not easily reproduced by changing `Default` controls. Do not export one-off variants that are just
  a single control value.
- When a component has multiple useful dimensions, prefer composite stories that compare those
  dimensions together. For example, a Button sizes story can show each size while applying variants,
  disabled state, and loading state across the set.
- Prefer real usage stories over artificial variant lists. Add composite examples that show how the
  component is used in a realistic interface when that teaches the contract better than another
  control.
- When a story `render` function is not pure consumer markup because it adds StoryLite/demo
  wrappers, storytelling layout, or explanatory content, define an explicit `source` snippet with
  the real code users should copy into their projects. Do not let StoryLite copy a demo-only
  `<main>` root or showcase wrapper.
- For complex components that need larger documentation, create a sibling Markdown file next to the
  story, e.g. `button.stories.md`, import it as HTML, and export it as the default documentation
  story for that component.

- Keep the `meta` declaration near the top of the file: after imports and before local types,
  constants, helpers, and story exports, e.g.

```ts
const meta: StoryLiteMeta = {
  title: 'Library/Overlays/Popover',
  parameters: {
    renderer: 'html',
    // Four per component since the core/theme split: base tokens, core, theme tokens, theme.
    css: [tokensCss, coreFloatingCss, corePopoverCss, themeCss, popoverCss, demoCss],
    defineCustomElements: defineTimelessElements,
  },
}
export default meta
```

- Keep reusable component anatomy factories/templates in their own files, e.g.
  `stories/accordion.html.ts`. These files should export typed `create*` functions, e.g.
  `export const createPopover = (props) => "<ui-popover> ..."`, plus any types needed by those
  props. The factories should represent the component contract markup and be reusable by both
  `render` and `source` functions.

- Keep story-only page wrappers, demo data, demo grids, and one-off scenario composition in the
  `.stories.ts` file unless they are shared across stories or useful as copyable component anatomy.

- Factory functions that accept story args should escape user-controlled values with the shared
  escaping helpers, e.g. `escapeHtml` and `escapeAttribute`.

- Shared demo layout styles can live in `stories/styles.css`. If a story needs component-specific
  demo styles, put them in a dedicated file, e.g. `stories/accordion.stories.css`, import it as
  `?raw` in the stories file, and append it to the `meta.parameters.css` array.

## Testing Guidelines

Principles:

- Confidence over coverage. Test behavior and outcomes; avoid brittle implementation-detail tests.

Do:

- E2E tests (Playwright): cover critical user flows and regression risks. Extend existing specs or
  add focused new ones in `apps/e2e`, keep tests small and well-named, use descriptive filenames ,
  tag slow suites with `@slow`, and run the suite before opening a PR.
- Unit tests: cover stable, high-value logic in `.ts` files, such as validators, transformers,
  evaluators, calculations, and edge cases. Keep assertions on inputs and outputs, colocate specs
  with the code they exercise (`utility.test.ts`), and mock network and storage boundaries.
- Manual QA, especially for releases: verify on staging and file bugs. If a bug is critical,
  backport and re-test.
- Run `pnpm test` after touching critical or complex flows, and `pnpm qa` before opening a PR.

Do not:

- Do not write component or UI unit tests for `apps/*`, e2e tests are fine like mentioned before.
- Do not add coverage-driven or low-signal tests.
- Do not write tests that lock implementation details, markup, snapshots, or create churn.
- Do not create mega or flaky E2E tests; avoid timing hacks and unstable dependencies.
